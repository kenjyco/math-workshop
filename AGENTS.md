# Repository instructions

Read [NORTH_STAR.md](NORTH_STAR.md), [.context/README.md](.context/README.md), and [README.md](README.md) before making changes. Follow the owner's currently authorized stage and bounded scope; a document describing future work does not authorize it.

## Content and stage discipline

- Establish accurate K–4 definitions, examples, visual representations, and concise parent bridges before full teaching explanations or activities.
- Stage A researches/plans read-only. Stage B authors goal specifications only. Stage C implements the approved foundation goals. Teaching and interactive work follow through separate handoffs.
- Preserve standard identifiers, grade/number limits, source provenance, and the difference between official expectations and chosen representations or instructional strategies.
- Verify reasoning, intermediate steps, notation, units, diagram meaning, and completion. A correct final answer alone does not prove a good example.
- Keep parent bridges close to relevant concepts without repetitive lesson prose. Avoid a mandatory README/lesson per goal; use the smallest coherent editable representation.
- Map conceptual relationships without turning them into access gates. Every explanation should be reusable; future exploration must expose other prerequisites and preserve the learner's work.
- No premature application framework, graph database, frontend plugin architecture, duplicated production frontend, or scaffolding unrelated to an approved goal.

## Repository boundaries

Keep reusable project content, necessary assets, goal specifications, and meaningful verification here. Keep plans about running development sessions, changing status, QA logs, commit plans, transcripts, generated releases, private source documents, and personal reference paths outside this repository. If an external recording destination is unavailable, report in the conversation; do not create a development-status directory here.

Every project file must remain useful in a standalone copy or clone. Repository-relative links may traverse between internal directories but must not escape the repository. No personal absolute paths, private external dependencies, assumptions about surrounding directories, or requirements to use a particular personal AI launcher.

## Review and Git discipline

Make small understandable changes. Verify substantive content independently and show evidence rather than relying only on a passing test count. Inspect untracked files as well as tracked diffs; an unborn repository can have substantial content with an empty ordinary diff.

Leave implementation uncommitted for owner QA. Do not stage or commit without an approved commit plan; owner QA alone does not authorize commit execution. One goal can span multiple coherent commits. Do not push, tag, publish, create another repository, or rewrite history without authorization.

Complete the work already authorized without repeated equivalent approval requests. Stop at actual stage, batch, and owner-review boundaries, and disclose real blockers or incomplete evidence.
